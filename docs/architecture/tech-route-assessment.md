# 微信小程序技术路线评估

## 结论摘要

经新下载的 LingoSnake 和官方微信小程序示例验证，最终确定以 `D:\project\learn` 为原生微信小程序基线；复用 LingoSnake 的纯学习核心组织方式，参考官方示例的组件、隐私和支付边界，不整仓替换。后端采用适配层优先，待真实接口和媒体验证后再收敛具体服务部署。

## 资产定位

| 项目 | 定位 | 复用方式 |
|---|---|---|
| `learn` | 原生微信小程序原型 | 页面、导航、课程详情、视频播放交互起点 |
| `7500km-android` | 业务最完整的参考实现 | 学习、复习、考试、课程、会员、接口字段和状态流转 |
| `Russion1` | 俄语词典原型 | 搜索模型、重音、词形、例句、历史和错误处理 |
| `Wordsearch` | 搜索/会员流程原型 | 低价会员入口、登录和支付流程参考 |
| `weixin` | Django 课程后端原型 | 课程、章节、视频、订单、进度关系参考，不直接生产复用 |
| `Harmony` | 背词交互 Demo | 单词卡片、复习、统计和音频体验参考 |
| `Russion_Stt` | 发音评测 AI 原型 | 后续独立服务，不放入小程序端 |

## 候选路线

### A. 直接复用既有 7500km API

验证成本最低，但依赖旧接口稳定性、登录协议、域名和小程序合规配置。应先用接口清单和真实响应做兼容性验证。

### B. 小程序适配层（确定优先）

小程序 → 适配层 → 既有 API/本地内容库。适配层屏蔽旧接口差异，签名、解密和密钥留在服务端，便于灰度和后续迁移。

### C. 独立内容服务

适合长期统一词典、课程和题库，但前期建设量大，不应在产品验证前启动全量迁移。

## 当前开发边界

- 继续使用原生 WXML/WXSS/JavaScript，不引入新框架。
- 暂不把现有 API 契约视为最终接口。
- 先抽取 `services/course.js`、`services/dictionary.js` 等前端业务层，页面不再直接拼接路径。
- 首个切片暂不包含支付、订阅和复杂登录。
- `learn/pages/course/video/` 是未注册的重复旧实现，不作为基线。
- `lingosnake-main/src/core/` 作为学习逻辑参考来源，需经俄语字段适配和服务端事件化改造后使用。
- `miniprogram-demo-master` 仅按需复制组件和合规示例，不引入其 Skyline、CloudBase 或完整分包结构。

## 决策门槛

首个切片完成后，依据接口成功率、字段覆盖、内容映射成本、登录/播放权限和部署合规性，选择 A、B 或 C。
